The natural next step is **v0.5.0**: turn the discovery engine from a crawler into a more explicit **acquisition/recognition pipeline**, with candidate deduplication, content-aware scheduling, network-event correlation, and a richer graph.

I’d make the next version focus on these architectural improvements:

1. **Separate observation from acquisition**
    * Page network events become first-class observations.
    * Avoid unnecessarily re-fetching resources already observed by the page.
    * Correlate `fetch`/XHR request → response → acquired resource.
2. **True candidate identity**
    * Deduplicate by canonical URL while retaining all discovery mechanisms.
    * One resource can be discovered through HTML, CSS, JavaScript, and network activity without being downloaded four times.
3. **Content-aware priority**
    * API/JSON/manifest: high priority.
    * HTML/navigation: high priority.
    * JS/CSS: medium.
    * images/media: lower.
    * deep candidates: progressively lower.
4. **Discovery graph**
    * Explicit nodes for resources.
    * Explicit edges for:  
        `HTML → link`,  
        `HTML → script`,  
        `JS → API`,  
        `CSS → image`,  
        `robots.txt → sitemap`,  
        `network → resource`, etc.
    * Multiple edges can point to the same resource.
5. **Provider confidence**
    * Providers can return multiple discoveries instead of exactly one.
    * Recognition confidence becomes part of scheduling.
6. **Candidate lifecycle**
    
    ```
    discovered
        ↓
    queued
        ↓
    claimed
        ↓
    acquiring
        ↓
    observed
        ↓
    recognized
        ↓
    expanded
        ↓
    completed
    ```
    
7. **Resource fingerprints**
    * status
    * content type
    * final URL
    * content length
    * optional lightweight hash
    * redirect relationship
8. **Better export**
    
    ```JSON
    {
      "nodes": [],
      "edges": [],
      "observations": [],
      "networkEvents": [],
      "statistics": {}
    }
    ```
    

That would make v0.5.0 substantially more than just “another crawler”: it would become a reusable **generic discovery framework** whose acquisition and recognition stages can later be replaced or extended for entirely different discovery domains.
