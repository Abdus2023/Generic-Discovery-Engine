Yes. The natural next step is **v0.4.0**, where the engine becomes more genuinely “discovery-engine” rather than just a recursive URL fetcher.

I’d add four things:

1. **Network-observation discovery** — observe `fetch`, XHR, and resource activity generated by the page.
2. **More candidate types** — API, manifest, sitemap, stylesheet, script, media, etc.
3. **Better scheduling** — priority + depth + retry backoff instead of simple priority sorting.
4. **A richer UI** — queue, requests, discoveries, failures, and provider types.

One important distinction: I would **not** make it automatically brute-force arbitrary URL paths. The useful DVB-inspired property here is _observation → validation → discovery → expansion_, not indiscriminate enumeration.

For the next version, the architecture would become:

```

                         └──────┬───────┘
```

### The biggest v0.4 improvement

> **Source sections:** `CAP-008`

I'd introduce a **discovery graph** rather than treating discoveries as a flat list:

```
page
 ├── HTML
 │    ├── /about
 │    ├── /api/config
 │    └── /static/app.js
 │
 ├── network
 │    ├── /api/session
 │    ├── /api/products
 │    └── /assets/config.json
 │
 └── metadata
      └── /sitemap.xml
```

That makes provenance meaningful:

```JavaScript
{
    candidate: "/api/products",
    discoveredBy: "/",
    mechanism: "network-fetch",
    confidence: 0.98
}
```

rather than merely:

```JavaScript
{
    url: "/api/products"
}
```

It also lets the exported JSON represent **how the engine learned something**, which is probably the most valuable part of the DVB-inspired architecture.

If you want to continue in that direction, I can produce the **complete v0.4.0 userscript**, building directly on the v0.3.0 above and adding the network observer + provenance graph + improved scheduler.
